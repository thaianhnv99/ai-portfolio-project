# Astra Trade: Lessons from Building a Multi-Site FX Trading Front-End

## Project Overview

Astra Trade is the front-end of an FX trading and risk pricing platform. Traders submit price requests, risk teams price and review them, and brokers monitor the resulting flow. One codebase builds three separate applications (user, admin and broker), selected at build time by a `SITE` environment variable. It is a client-rendered single-page app, so there is no server-side rendering involved.

## Main Technologies

- React 18 and TypeScript in strict mode
- Vite 6 with the SWC plugin
- MUI Joy UI (dark theme only) and Emotion
- Zustand 5 with persist and immer for state
- Axios for the API layer and Socket.IO client for live updates
- React Hook Form for complex forms
- BigNumber.js for financial calculations, to avoid floating point errors
- Chart.js, Day.js and TanStack Virtual

## The Challenge: Long Tables That Update in Real Time

Tables are the heart of the product: executions, indications, flow alerts. They started paginated. The product team then asked for scroll-to-load-more, and three problems appeared.

First, race conditions. If a user changed a filter while a request was still in flight, a late response could overwrite the freshly reset list. Second, live data. Socket events must refresh the list without throwing away what the user has already scrolled through. Third, rendering cost. After a few hundred rows, scrolling and column resizing became sluggish, because every column drag re-rendered every row.

## How I Solved It

I moved all data logic into one hook, `useLazyList`. It keeps a request counter in a ref, and only the latest request is allowed to write state, so stale responses are dropped. Any search, filter or sort change rewinds the page to 1. A refresh function reloads every batch loaded so far in parallel, which is what socket events and edits call.

For rendering, I virtualized the table body, but only once more than 80 rows are loaded, so short tables stay simple. Pages scroll differently on each screen, so instead of following one scroll container, the visible window is derived from the position of the table body in the viewport, read from a capture-phase scroll listener throttled with `requestAnimationFrame`. Two spacer rows stand in for the rows that are off screen. I also memoised the body rows and made the layout effects set state only when a value actually changed, so dragging a column no longer re-renders them.

Finally, the feature sits behind a flag. A build-time variable or a `localStorage` value brings back pagination without a rebuild.

## Lessons Learned

1. Guard every async list against stale responses. A simple request id prevents a whole class of confusing bugs.
2. Hide risky UX changes behind a feature flag. It made the release safe and demos easy.
3. Virtualize only when needed. A threshold keeps small tables simple.
4. Do not assume one scroll container. Reading element position from the viewport is more portable.
5. Hide complexity inside a hook. The screens stayed unchanged while the behavior behind them was replaced.
